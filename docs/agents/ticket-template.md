# 票面骨架

开票照这个骨架写（`gh issue create --title "..." --body "..."`，操作见
`docs/agents/issue-tracker.md`）。

**票面是 agent 和评审共同的唯一事实来源**（`AGENTS.md` §3）——所以「跟什么比」
这类话要写在**票面**里，不能只留在 agent 的对话里：agent 照票面做，评审照票面核。

## 骨架

````markdown
## What to build

<从用户视角说这一票让什么变得可能；不要写成逐层的实现清单>

## 现在的样子 / 根因

<现在是什么样、为什么是这样；查实了再写，别猜>

## 要做的

1. <一条一件事；要说清「为什么这样做」，或者「做法的几种选择与取舍」>

## Acceptance criteria

- [ ] <可核对的一条>
- [ ] ...

## Blocked by

- <挡着它的那几张票，或「无（可以立刻开工）」>

## 纪律

- 用 MyGo 原生写，不要 webview（`AGENTS.md` §5）；不打真 B 站接口；不新增依赖。
- ⚠️ **别整包跑 `./internal/ui/`**（`AGENTS.md` §1）。
````

## 界面票固定要有的那几条

凡是动了界面的票，验收里都要有这两条：

- [ ] 默认验收命令绿（`AGENTS.md` §1，test 那一步**不带** `-trimpath`）
- [ ] 动了界面行为 →
      `GOGC=10 go test ./internal/ui/ -count=3 -timeout 5m -run '<你改到的那几条用例名>'`

## UI 票：必须再多一条「视觉审查」

**凡是动了界面「摆布」的票**——布局 / 间距 / 层级 / 密度 / 对齐这五项里任何一项
动了就是——验收里**必须**有一条：

````markdown
- [ ] **视觉审查**：对着 <参考>（上游 Biu `<文件:行号>` / 用户 <日期> 给的那张图 /
      `DESIGN.md` §<某节>）逐张看了出图，五项（布局 / 间距 / 层级 / 密度 / 对齐）
      都过；收尾说明里逐条写了差在哪儿（差多少、改没改）；不合格的已经改了并重新出图
````

细则见 `AGENTS.md` §1《UI 票的验收必须有一次「视觉审查」》。

**参考要写具体**：「对着上游核」不算——要写上游哪个文件哪一行、或者用户哪天的哪张
图、或者 `DESIGN.md` 哪一节。写不出来就是**还没查**，不是「没有参考」。

⚠️ **颜色、字号、动效时序不在这五项里**——那些票走 `DESIGN.md` §八 的「逐像素
采样」和各自专项的判据（本仓库有几十条颜色判据的票），**别拿视觉审查替代它们**。

⚠️ **不要写「逐像素比对参考图」**：出图本身不确定（同一份代码两次出图有几十张会
不一样），要比像素得先跑两遍 HEAD 当对照——那是另一回事。
