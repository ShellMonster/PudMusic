# Spec：收藏夹隐藏管理 / 播放断点续播 / 歌词缓存防串歌 / 失效收藏墓碑

> 状态：ready-for-agent。本地 spec，不上 GitHub。
> 日期：2026-11-03。

## Problem Statement

四个独立但同批次的问题：

1. **收藏夹藏了就找不回来**。侧栏收藏夹右键菜单里有「隐藏」，藏掉的 id 写进
   `hiddenMenuKeys` 设置项——但整个应用里**没有任何一个界面能把它放回来**。
   用户一旦藏错，唯一的补救是手工编辑设置文件。更糟的是：在 B 站网页上删掉
   收藏夹之后，那笔 id 永远留在设置文件里，成为无人认领的孤儿数据。

2. **关掉应用再开，正在听的那一首从头开始**。位置只在内存里（`a.position`，
   每 50ms 一拍），退出时不落盘。听一个两小时的合集 / 直播录像，中途关掉
   应用，下次打开要从头找自己听到哪了。

3. **歌词缓存会串歌**。歌词缓存按条目 key（`lyricKeyOf`：bvid / sid / 本地
   路径）存取，不校验这首歌是谁。同名翻唱、换源后拿到的是另一首歌的歌词、
   用户手动搜错又删不掉——缓存里那份错的永远是对的，因为它只认 key。

4. **收藏夹里失效的条目直接消失**。UP 主把稿件设为仅自己可见、或者删掉，
   收藏夹刷新回来那一条就没了。用户看到的现象是「收藏夹数量对不上」，
   但不知道是为什么——「少了」和「没拉到」长得一样。

## Solution

1. **收藏夹**：设置页「菜单设置」Tab 里加一组收藏夹可见性管理，两组收藏夹
   逐行勾选，勾上 = 侧栏可见、取消 = 隐藏，实时生效；隐藏项在 B 站侧删除后
   仍能在设置页看见并清掉。

2. **断点续播**：退出时把「正在放的这一条 + 进度 + 队列上下文」落盘；下次
   启动恢复队列，并把进度 seek 回上次的位置（留几秒回退）。

3. **歌词防串歌**：缓存条目里记下这份歌词是为「哪个标题 + 哪个歌手」存的；
   读取时校验——对不上就当没缓存，走重新拉取，而不是把错的歌词放出来。

4. **失效墓碑**：收藏夹刷新时，详情接口查不到的条目**保留**在本地，标记
   「已失效」，界面上画出来但置灰、不可播，附一句「UP 主可能已删除或设为
   仅自己可见」，而不是整条消失。

## User Stories

收藏夹可见性：

1. As a 用户，我把收藏夹藏起来之后想放回来，这样我不用去改设置文件。
2. As a 用户，我想在设置页看到「哪些收藏夹被藏了」，这样我能一次管理全部，
   而不是凭记忆去侧栏数。
3. As a 用户，我在 B 站删了收藏夹之后，设置里那笔隐藏的 id 也能清掉，
   这样它不会永远留在我的设置文件里。
4. As a 用户，我在设置页勾选/取消之后**立刻**看到侧栏变化，这样我知道
   操作生效了。

断点续播：

5. As a 用户，我中途关掉应用，下次打开能从我上次停的那一秒接着放，
   这样长音频（合集、广播剧、直播录像）不用从头找。
6. As a 用户，恢复播放时进度**往回退几秒**，这样我能接住上下文，
   而不是从切走的那一刀硬接。
7. As a 用户，我上一次听的是队列中间的歌，恢复之后队列还是原来那个队列，
   这样我能继续往下放。
8. As a 用户，上次的歌后来在 B 站被删了 / 取不到流，恢复时应用告诉我而不是
   卡在那。

歌词防串歌：

9. As a 用户，同名两首歌不会串歌词，这样翻唱、同名曲各自显示对的词。
10. As a 用户，我手动搜错一份歌词之后，下一次不会还把那份错的当缓存，
    这样我能纠正自己的错误。
11. As a 用户，歌名或歌手改了（B 站编辑稿件）之后，旧缓存不认，重新拉，
    这样我不至于看一份不属于这首歌的词。

失效墓碑：

12. As a 用户，收藏夹里的歌被 UP 主删掉之后，我在列表里还能看到「这一条
    没了」，这样我不会以为应用少拉了。
13. As a 用户，失效的条目**点不动**（或者点了说一句原因），这样我不会
    以为应用坏了。
14. As a 用户，失效条目在 B 站恢复可见之后，刷新一次就能回来，
    这样墓碑不是永久的。

## Implementation Decisions

### 收藏夹可见性（已落地的部分，此处固定为事实）

- 数据源：沿用 `Settings.HiddenMenuKeys`（`[]string`，十进制收藏夹 id）。
  不新增设置键——菜单项和收藏夹共用一份名单，Biu 格式兼容。
- 入口：设置页 → 「菜单设置」Tab → 「收藏夹」分组，两组各一行一个
  Checkbox，勾上 = `!hiddenMenuKeys 包含 id`。
- 孤儿清理：`hiddenMenuKeys` 里能 `ParseInt` 成功、但两组接口返回里都没有
  的 id，单列一行「收藏夹 {id}（已不在列表里）」，可勾选清掉。
- 实时生效：设置写回走既有的 `applySetting`，侧栏每帧从设置读，
  天然下一帧就更新。

### 断点续播

- 新增设置键 `playbackResume`（对象，`{trackKey, positionMs, queueId?}`，
  只加可选键不涨 `SchemaVersion`，和 `SideMenuCollectionOrder` 同一个先例）。
- **写入时机**：切歌那一刻（`position` 被清零之前）和 `App.Close` 退出前
  各写一次。不每拍写——50ms 一次的写盘是纯粹的浪费。
- `trackKey` 用 `lyricKeyOf` 那同一套身份（bvid / sid / 本地路径），
  不是内存对象——重启后队列条目是新拉的，只能按 id 对。
- **恢复**：启动时如果设置里有这一条，恢复队列（QueueSnapshot 本来就落盘）
  → 找到 trackKey 那一条 → seek 到 `positionMs - 3s`（几秒回退，下限 0）。
- **取不到流的处理**：恢复那一首的取流失败照 `unplayable.go` 那一套说原因，
  不静默卡在 0:00。

### 歌词缓存防串歌

- `lyrics.Entry` 加两个可选字段 `Title`、`Artist`（json `omitempty`）。
- 写缓存时把当前条目的标题、歌手一起存；读缓存时把这两个值和当前条目对——
  **对不上就当没有**（返回 ok=false 或歌词为空），走重新拉取路径。
- 手动搜来的歌词（origin=search）**也校验**——用户可能搜错。
- 兼容：老缓存文件没有这两个字段 → 视为「未知」，按**现在**的行为处理
  （不校验直接放行），不强制迁移。

### 失效收藏墓碑

- `app.Favorite` 加 `Valid bool`（或单独 `Favorite.Invalid bool`），
  详情接口返回里查不到的条目在刷新时置为失效，**不从列表删除**。
- 侧栏那一行：置灰（`TextMuted`）、不响应播放动作，行尾或名称下加
  「已失效」标记；右键菜单只留「取消收藏」和「隐藏」，播放/加队列置灰。
- 空列表判定不变：一组全失效时仍算有内容（画得出墓碑），不落「还没有
  收藏夹」那句。
- 「我收藏的」那组同理——接口本来就是别人的收藏夹，失效同样留墓碑。

## Testing Decisions

好测试的样子：只测外部行为（画面上的字、磁盘上的文件、接口返回的数据流），
不摸内部实现。沿用本仓库现有模式：

- **收藏夹可见性**：`internal/ui/settings_tab_favorites_test.go`（已写，本 spec
  是对它的追认）——`shellOnSettings` + `SetFavorites` + `clickCheckbox` 断言
  画面文字和 `SettingsSnapshot().HiddenMenuKeys`。
- **断点续播**：`internal/app/` 层测「切歌/退出 → 设置里写了什么」；`internal/ui/`
  层测「启动 → 播放条进度不是 0:00」。先 art `playback_state.go` 里已有的
  `position`/`PlayReport` 测试形状。
- **歌词防串歌**：`internal/service/lyrics/` 的 cache 测试（`Entry` 新字段的
  存取、对不上就丢）+ `internal/app/lyrics_test.go` 端到端（放 A 歌 → 缓存
  写入 → 放同 key 但不同标题的 B 歌 → 拿到的不是 A 的词）。仿
  `TestLyricsOffset` 的形状。
- **失效墓碑**：`internal/app/favorites_test.go` 层测「刷新时接口少返回
  一条 → Favorites.Snapshot 里那一条还在但标记失效」；`internal/ui/`
  层测侧栏画出置灰行 + 右键菜单里播放项消失。仿
  `sidebar_favorites_empty_test.go` 的形状。

默认验收不变（`AGENTS.md` §1）：`go build -trimpath -p 4 ./... &&
go vet -trimpath -p 4 ./... && go test -p 4 $(go list ./... | grep -v '/internal/ui$')`。

UI 票验收按 `docs/agents/ticket-template.md`：收藏夹可见性（已完成）、
失效墓碑（侧栏行样式变了）**都带视觉审查一条**——对着 Biu 的
`side/collection/index.tsx` 失效态和本仓库 `DESIGN.md` 侧栏规范逐张看出图。

## Out of Scope

- 音频流档位（杜比 / Hi-Res 的 `fnval=4048` 选流）：本项目 `quality.go` 已经
  把 `dash.dolby` / `dash.flac` / `dash.audio[]` 分好档，`fnval` 也已经是
  4048——这件事**已做**，不在本 spec。
- 分 P 展开收藏夹：B 站多分 P 视频拆成多条，工程量和收藏夹语义纠缠太大，
  单独开。
- 动态合并歌单 / 歌单置顶 / 本地自建歌单：本地歌单模型整体另开 spec。
- 稍后再看 / 历史上报 B 站：`ReportPlayHistory` 已有开关和接口，本 spec 不动。
- B 站装扮主题（garb）、外部歌单导入（网易云/QQ）、首页音乐趣事：
  均不在本批。

## Further Notes

- `hiddenMenuKeys` 一份名单两伙人写的纪律已经在 `mergeHiddenMenuKeys` 里，
  收藏夹这组沿用同一套 merge 逻辑，不新增写路径。
- 断点续播的「回退几秒」取 3s：长音频（>10min）回退 5s 可能更友好，
  第一版统一 3s，界面不暴露这个数。
- 失效墓碑**不能**自动从 `hiddenMenuKeys` / `SideMenuCollectionOrder` 里清
  id——失效≠删除，墓碑保留正是为了「B 站恢复了还能回来」。
